# 1. Что такое драйвер? Основы

## 1.1. Простая аналогия

Представь, что ты приходишь в ресторан в другой стране. Ты хочешь заказать еду, но не знаешь местного языка. **Переводчик** помогает тебе общаться с поваром.

В компьютере:
- **Ты** = приложение (браузер, игра, текстовый редактор)
- **Повар** = устройство (мышь, клавиатура, видеокарта)
- **Переводчик** = драйвер

**Драйвер** — это программа-переводчик между операционной системой и устройством.

## 1.2. Зачем нужен драйвер?

Каждое устройство "говорит" на своём языке:
- Мышь от Logitech говорит на одном "языке"
- Мышь от Razer — на другом
- Клавиатура — на третьем

Если бы каждое приложение (игра, браузер) должно было знать, как работать со ВСЕМИ устройствами — это был бы кошмар.

**Драйвер решает проблему:**
```
Приложение → "Хочу узнать, куда двигается мышь"
     ↓
Операционная система → "Спрошу у драйвера"
     ↓
Драйвер → "Сейчас спрошу у мыши на её языке"
     ↓
Мышь → (отправляет данные на своём языке)
     ↓
Драйвер → "Переведу в понятный формат"
     ↓
Операционная система → "Вот тебе координаты"
     ↓
Приложение → "Спасибо, двигаю курсор"
```

## 1.3. Где "живёт" драйвер?

В компьютере есть два мира:

### Пространство пользователя (User Space)
- Здесь работают обычные программы: браузер, игры, текстовые редакторы
- Они НЕ МОГУТ напрямую обращаться к устройствам (для безопасности)
- Если программа сломается — это не страшно, просто закроется

### Пространство ядра (Kernel Space)
- Здесь работает **ядро операционной системы** (Linux kernel)
- Здесь работают **драйверы**
- Они МОГУТ напрямую обращаться к устройствам
- Если драйвер сломается — может упасть вся система (kernel panic)

```
┌─────────────────────────────────────┐
│   Пространство пользователя         │
│   (браузер, игры, редакторы)        │
│   ❌ НЕ может трогать устройства     │
└─────────────────────────────────────┘
         ↕ (системные вызовы)
┌─────────────────────────────────────┐
│   Пространство ядра (Kernel)        │
│   ✅ Драйверы                        │
│   ✅ Может трогать устройства        │
└─────────────────────────────────────┘
         ↕ (прямой доступ)
┌─────────────────────────────────────┐
│   Физические устройства             │
│   (мышь, клавиатура, диск)          │
└─────────────────────────────────────┘
```

**Твой драйвер работает в пространстве ядра** — поэтому он может перехватывать события мыши и модифицировать их.

# 2. Архитектура компьютера и операционной системы

## 2.1. Процессор и кольца защиты

**Процессор (CPU)** — это "мозг" компьютера. Он выполняет инструкции программ.

Для безопасности процессор имеет уровни привилегий (кольца защиты):

```
┌──────────────────────────────────┐
│  Ring 0 (самый привилегированный)│
│  Ядро ОС, драйверы               │
│  ✅ Полный доступ ко всему        │
└──────────────────────────────────┘
         ↕
┌──────────────────────────────────┐
│  Ring 3 (обычные программы)      │
│  Браузер, игры, редакторы        │
│  ❌ Ограниченный доступ           │
└──────────────────────────────────┘
```

**Ring 0** — максимальные права, может делать всё (ядро, драйверы)
**Ring 3** — обычные программы, защищены от прямого доступа к устройствам

Когда программе нужно что-то от устройства, она делает **системный вызов (syscall)** — просит ядро сделать это за неё.

## 2.2. Ядро операционной системы

**Ядро (Kernel)** — это центральная часть операционной системы. Оно:
- Управляет памятью
- Распределяет время процессора между программами
- Работает с устройствами через драйверы
- Защищает программы друг от друга

**Linux Kernel** — это ядро операционной системы Linux. Оно монолитное (всё в одном большом блоке), но поддерживает **модули** — драйверы, которые можно загружать/выгружать без перезагрузки.

**Твой драйвер — это модуль ядра Linux.**

## 2.3. MMU (Memory Management Unit)

**MMU** — это специальный чип в процессоре, который управляет памятью.

### Зачем нужен MMU?

Представь, что у тебя несколько программ работают одновременно:
- Браузер думает, что его память начинается с адреса 0x1000
- Игра тоже думает, что её память с адреса 0x1000

Если бы они работали с реальными адресами — они бы перезаписывали данные друг друга!

**MMU решает проблему:**
```
Виртуальная память (программа видит)
Адрес 0x1000 в браузере
         ↓
       MMU (переводит)
         ↓
Физическая память (реальный чип)
Адрес 0x5A3F2000
```

**Каждая программа видит свой "виртуальный мир" памяти**, а MMU переводит это в реальные адреса.

### MMU в контексте драйверов

Драйверы работают в ядре и могут:
- Обращаться к **физической памяти** напрямую
- Создавать **маппинг** (отображение) устройств в память

**В твоём драйвере MMU используется неявно** — когда ты выделяешь память через `kzalloc()`, MMU выделяет физическую память и даёт тебе виртуальный адрес.

# 3. Как компьютер общается с устройствами

## 3.1. Port-Mapped I/O vs Memory-Mapped I/O

Устройства (мышь, клавиатура) нужно как-то читать/писать. Есть два способа:

### Port-Mapped I/O (портовый ввод-вывод)

Процессор имеет специальные инструкции `IN` и `OUT` для чтения/записи в порты:

```
OUT порт 0x60, значение 0x42  # Записать 0x42 в порт клавиатуры
```

Порты — это отдельное адресное пространство (не память).

**Пример:** старые клавиатуры PS/2 работают через порт 0x60.

### Memory-Mapped I/O (память-отображённый ввод-вывод)

Устройство "притворяется" обычной памятью. Когда ты пишешь по определённому адресу — на самом деле пишешь в устройство:

```
*(0xFEC00000) = 0x42;  # Записать в регистр устройства
```

Этот адрес физически подключён к устройству, а не к RAM.

**Пример:** современные USB-контроллеры используют Memory-Mapped I/O.

### В твоём драйвере

**Ты НЕ работаешь с портами/памятью напрямую!**

Ты работаешь через **абстракцию подсистемы ввода Linux** — получаешь уже готовые события от USB HID драйвера, который работает с портами/памятью за тебя.

## 3.2. Прерывания (Interrupts)

**Прерывание** — это способ устройства "привлечь внимание" процессора.

### Как работают прерывания?

Представь, что ты читаешь книгу. Вдруг звонит телефон:
1. Ты **прерываешь** чтение
2. Берёшь телефон (обработчик прерывания)
3. Отвечаешь на звонок
4. Кладёшь трубку
5. **Возвращаешься** к книге

Так же работает процессор:

```
Процессор выполняет программу
         ↓
    (движение мыши)
         ↓
Мышь → USB контроллер → "Прерывание!"
         ↓
Процессор прерывает программу
         ↓
Запускает обработчик прерывания (драйвер USB)
         ↓
Драйвер USB читает данные от мыши
         ↓
Передаёт в подсистему ввода
         ↓
Процессор возвращается к программе
```

### IRQ (Interrupt Request)

Каждое прерывание имеет номер — **IRQ** (линия запроса прерывания).

Пример:
- IRQ 1 — клавиатура
- IRQ 12 — мышь PS/2
- IRQ 16-23 — USB контроллер

Когда устройство генерирует прерывание — процессор смотрит таблицу обработчиков и вызывает нужный драйвер.

### В твоём драйвере

**Ты НЕ обрабатываешь прерывания напрямую!**

USB драйвер обрабатывает прерывания от мыши → передаёт события в Input Core → Input Core вызывает твой `event_filter()`.

Ты работаешь на более высоком уровне абстракции.

## 3.3. DMA (Direct Memory Access)

**DMA** — это способ устройства читать/писать память **без участия процессора**.

### Зачем нужен DMA?

Представь, что тебе нужно переписать книгу:
- **Без DMA:** ты читаешь каждую строку, запоминаешь, пишешь. Долго!
- **С DMA:** ты даёшь книгу копировальному аппарату, и он копирует сам.

В компьютере:

```
Без DMA:
USB контроллер → Прерывание → CPU читает байт → Записывает в RAM
(повторяется для каждого байта)

С DMA:
CPU → "Устройство, копируй данные в адрес 0x12345000"
USB контроллер → (копирует сам через DMA) → RAM
Когда закончил → Прерывание → CPU → "Готово!"
```

**DMA экономит время процессора** — устройство само пишет/читает память.

### В твоём драйвере

**DMA используется USB HID драйвером** для чтения данных от мыши через USB. Но ты это не видишь — работаешь уже с готовыми событиями.

## 3.4. IOCTL (Input/Output Control)

**IOCTL** — это способ программы отправлять команды устройству.

### Как работает IOCTL?

Программа открывает файл устройства (например, `/dev/input/event0`) и делает системный вызов `ioctl()`:

```c
int fd = open("/dev/input/event0", O_RDONLY);
ioctl(fd, EVIOCGNAME(256), name);  // Получить имя устройства
```

`ioctl()` — это "универсальный" системный вызов для управления устройством.

### Коды IOCTL

Каждая команда имеет числовой код. Для устройств ввода:
- `EVIOCGNAME` — получить имя устройства
- `EVIOCGRAB` — захватить устройство эксклюзивно
- `EVIOCGLED` — получить состояние LED клавиатуры

### В твоём драйвере

**Ты не используешь IOCTL напрямую**, но:
- Твой драйвер вызывает `input_grab_device()` — это аналог `EVIOCGRAB`
- Пользовательские программы могут использовать IOCTL для работы с виртуальной мышью

# 4. Подсистема ввода Linux

## 4.1. Что такое Input Subsystem?

**Input Subsystem** — это часть ядра Linux, которая управляет устройствами ввода (клавиатуры, мыши, джойстики).

### Зачем нужна подсистема?

Раньше каждый драйвер мыши создавал свой файл (`/dev/mouse0`, `/dev/psaux`, etc.). Программы не знали, какой файл использовать.

**Input Subsystem решила проблему:**
- Все устройства ввода регистрируются в одном месте
- Создаётся единый интерфейс `/dev/input/eventX`
- Программы работают с любыми устройствами одинаково

## 4.2. Архитектура Input Subsystem

```
┌─────────────────────────────────────────────┐
│  Пользовательское пространство              │
│  (приложения: игры, X11, Wayland)           │
└─────────────────────────────────────────────┘
         ↕ (чтение /dev/input/eventX)
┌─────────────────────────────────────────────┐
│  Event Handlers (evdev, mousedev)           │
│  Создают /dev/input/eventX                  │
└─────────────────────────────────────────────┘
         ↕ (события)
┌─────────────────────────────────────────────┐
│  Input Core (ядро подсистемы)               │
│  Управляет устройствами и событиями         │
└─────────────────────────────────────────────┘
         ↕ (регистрация устройств)
┌─────────────────────────────────────────────┐
│  Input Device Drivers (USB HID, PS/2, etc)  │
│  Драйверы физических устройств              │
└─────────────────────────────────────────────┘
         ↕ (прерывания)
┌─────────────────────────────────────────────┐
│  Физические устройства (мышь, клавиатура)   │
└─────────────────────────────────────────────┘
```

### Компоненты:

1. **Input Device Drivers** — драйверы конкретных устройств (USB, PS/2)
2. **Input Core** — ядро подсистемы, управляет событиями
3. **Event Handlers** — обработчики, создающие `/dev/input/eventX`
4. **Input Handlers** — **ТУТ ТВОЙ ДРАЙВЕР!** Перехватчики событий

## 4.3. Структура input_dev

**input_dev** — это структура данных, представляющая устройство ввода.

```c
struct input_dev {
    const char *name;           // Имя устройства
    struct input_id id;         // ID (vendor, product)

    unsigned long evbit[BITS_TO_LONGS(EV_CNT)];  // Какие типы событий поддерживает
    unsigned long keybit[...];  // Какие клавиши
    unsigned long relbit[...];  // Какие относительные оси (X, Y)

    // ... много других полей
};
```

Когда USB драйвер обнаруживает мышь:
1. Создаёт `input_dev`
2. Заполняет поля (имя, ID, поддерживаемые события)
3. Регистрирует через `input_register_device()`

**Твой драйвер тоже создаёт `input_dev`** для виртуальной мыши!

## 4.4. События (input_event)

События передаются через структуру `input_event`:

```c
struct input_event {
    struct timeval time;  // Время события
    __u16 type;          // Тип: EV_KEY, EV_REL, EV_ABS, EV_SYN
    __u16 code;          // Код: KEY_A, REL_X, BTN_LEFT
    __s32 value;         // Значение
};
```

### Типы событий для мыши:

**EV_REL** (относительное движение):
- `REL_X` — сдвиг по X (например, +5 пикселей)
- `REL_Y` — сдвиг по Y
- `REL_WHEEL` — прокрутка колеса

**EV_KEY** (кнопки):
- `BTN_LEFT` (272) — левая кнопка
- `BTN_RIGHT` (273) — правая
- `BTN_MIDDLE` (274) — средняя
- value = 1 (нажата), 0 (отпущена)

**EV_SYN** (синхронизация):
- `SYN_REPORT` — "пакет событий завершён"

### Пример: движение мыши вправо

```
Event: type=EV_REL, code=REL_X, value=5
Event: type=EV_SYN, code=SYN_REPORT, value=0
```

Мышь сдвинулась на 5 пикселей вправо.

### Пример: движение мыши + нажатие кнопки

```
Event: type=EV_REL, code=REL_X, value=3
Event: type=EV_REL, code=REL_Y, value=-2
Event: type=EV_KEY, code=BTN_LEFT, value=1
Event: type=EV_SYN, code=SYN_REPORT, value=0
```

Мышь сдвинулась (+3, -2) и нажата левая кнопка.

## 4.5. Input Handler (твой драйвер использует это!)

**Input Handler** — это механизм перехвата событий **до того, как они попадут в /dev/input/eventX**.

```c
struct input_handler {
    bool (*filter)(struct input_handle *handle,
                   unsigned int type, unsigned int code, int value);
    int (*connect)(struct input_handler *handler, struct input_dev *dev, ...);
    void (*disconnect)(struct input_handle *handle);

    const struct input_device_id *id_table;  // Какие устройства обрабатывать
    const char *name;
};
```

### Как работает Input Handler?

```
Мышь → USB драйвер → input_report_rel() → Input Core
                                              ↓
                              Input Core вызывает всех Handler'ов
                                              ↓
                                    Твой filter() вызывается
                                              ↓
                              Если вернёшь true — событие блокируется
                              Если вернёшь false — событие идёт дальше
                                              ↓
                                       evdev → /dev/input/eventX
                                              ↓
                                      Приложение читает
```

**Твой драйвер регистрирует Input Handler** и перехватывает события от физической мыши!

# 5. Как работает мышь на низком уровне

## 5.1. USB и HID (Human Interface Device)

Большинство современных мышей подключаются через **USB** и используют протокол **HID**.

### Что такое USB?

**USB (Universal Serial Bus)** — это стандарт подключения устройств. Он:
- Обеспечивает питание устройству (5V)
- Передаёт данные (до 480 Мбит/с для USB 2.0)
- Поддерживает "горячее" подключение (Plug and Play)

### Структура USB:

```
Компьютер
    ↓
USB Host Controller (в материнской плате)
    ↓
USB Hub (разветвитель)
    ↓
USB устройства (мышь, клавиатура, флешка)
```

### USB дескрипторы

Когда ты подключаешь мышь, она отправляет **дескрипторы** — описание самой себя:

```
Device Descriptor:
  idVendor: 0x046d (Logitech)
  idProduct: 0xc08b (G502)
  bDeviceClass: 0 (определяется в Interface)

Interface Descriptor:
  bInterfaceClass: 3 (HID)
  bInterfaceSubClass: 1 (Boot Interface)
  bInterfaceProtocol: 2 (Mouse)
```

Это как паспорт устройства — операционная система читает его и понимает: "Это мышь!"

## 5.2. Что такое HID?

**HID (Human Interface Device)** — это стандарт для устройств ввода.

### HID Report Descriptor

Мышь отправляет **HID дескриптор отчёта** — описание формата данных:

```
HID Report Descriptor:
  Usage Page: Generic Desktop
  Usage: Mouse
  Collection: Application
    Usage: Pointer
    Collection: Physical
      Usage Page: Buttons
      Usage Minimum: 1 (кнопка 1)
      Usage Maximum: 5 (кнопка 5)
      Logical Minimum: 0
      Logical Maximum: 1
      Report Count: 5 (5 кнопок)
      Report Size: 1 (1 бит на кнопку)
      Input: (Data, Variable, Absolute)

      Usage Page: Generic Desktop
      Usage: X
      Usage: Y
      Usage: Wheel
      Logical Minimum: -127
      Logical Maximum: 127
      Report Count: 3 (X, Y, Wheel)
      Report Size: 8 (8 бит = 1 байт)
      Input: (Data, Variable, Relative)
```

Это описание говорит: "Я буду отправлять 5 бит для кнопок + 3 байта для X/Y/Wheel".

### HID Report (данные от мыши)

Когда ты двигаешь мышь, она отправляет **HID отчёт**:

```
Байт 0: [кн5][кн4][кн3][кн2][кн1][0][0][0]
Байт 1: X (знаковое число -127..127)
Байт 2: Y (знаковое число -127..127)
Байт 3: Wheel (знаковое число)
```

Пример:
```
0x01 0x05 0xFE 0x00
```
- Байт 0 = 0x01 = 0b00000001 → нажата кнопка 1 (левая)
- Байт 1 = 0x05 = +5 → сдвиг X на +5
- Байт 2 = 0xFE = -2 → сдвиг Y на -2
- Байт 3 = 0x00 → колесо не крутилось

## 5.3. USB HID драйвер в Linux

**usbhid** — это драйвер ядра Linux, который:
1. Получает прерывания от USB контроллера
2. Читает HID отчёты от мыши
3. Парсит их по HID дескриптору
4. Преобразует в события Input Subsystem

```c
// Внутри usbhid драйвера (упрощённо):

void hid_input_report() {
    u8 *data = /* HID отчёт */;

    // Парсим кнопки
    if (data[0] & 0x01) {
        input_report_key(input_dev, BTN_LEFT, 1);
    }

    // Парсим движение
    s8 dx = data[1];
    s8 dy = data[2];
    input_report_rel(input_dev, REL_X, dx);
    input_report_rel(input_dev, REL_Y, dy);

    // Синхронизация
    input_sync(input_dev);
}
```

**input_report_rel()** и **input_sync()** отправляют события в Input Core.

## 5.4. PnP (Plug and Play)

**Plug and Play** — это технология автоматического обнаружения устройств.

### Как работает PnP?

1. Ты подключаешь мышь
2. USB контроллер обнаруживает новое устройство (по изменению напряжения на линии)
3. USB контроллер генерирует **прерывание**
4. USB драйвер ядра обрабатывает прерывание
5. USB драйвер читает дескрипторы устройства
6. USB драйвер ищет подходящий драйвер (usbhid для HID устройств)
7. usbhid инициализирует мышь
8. Мышь готова к работе!

Всё это происходит за доли секунды.

### PnP в твоём драйвере

Когда usbhid регистрирует мышь в Input Subsystem → Input Core вызывает **твой connect()**.

Твой `mouse_connect()` вызывается автоматически благодаря PnP!

# 6. Твой драйвер: полный разбор

Теперь, зная всю теорию, разберём твой драйвер **от физического движения мыши до курсора на экране**.

## 6.1. Что делает твой драйвер?

**Задача:** автоматически менять чувствительность (DPI) мыши в зависимости от скорости движения.

- Медленно двигаешь → DPI 50% → точность
- Средне → DPI 100% → норма
- Быстро → DPI 200% → скорость

## 6.2. Полный путь события: от движения мыши до курсора

### Шаг 1: Физическое движение

Ты двигаешь мышь на 1 см вправо.

### Шаг 2: Оптический сенсор

Мышь имеет оптический сенсор (маленькая камера), который фотографирует поверхность:
- Делает 1000-8000 кадров в секунду
- Сравнивает кадры → вычисляет сдвиг
- Сенсор определяет: "Сдвиг +127 единиц по X"

### Шаг 3: Микроконтроллер мыши

В мыши есть маленький процессор, который:
- Читает данные сенсора
- Формирует HID отчёт: `[0x00, 0x7F, 0x00, 0x00]`
  - Кнопки не нажаты (0x00)
  - X = +127 (0x7F)
  - Y = 0
  - Wheel = 0

### Шаг 4: USB передача

Микроконтроллер отправляет данные через USB:
```
Мышь → USB кабель → USB порт компьютера → USB контроллер
```

### Шаг 5: USB контроллер генерирует прерывание

USB контроллер (чип на материнской плате):
1. Получает данные от мыши через DMA в память
2. Генерирует **прерывание** (IRQ 16, например)

### Шаг 6: USB драйвер обрабатывает прерывание

Процессор прерывает текущую работу:
```
Процессор выполняет программу
         ↓
    Прерывание!
         ↓
CPU смотрит таблицу обработчиков IRQ
         ↓
Запускает USB драйвер (usbhid)
```

### Шаг 7: usbhid парсит HID отчёт

```c
// Внутри usbhid драйвера:
u8 *data = /* [0x00, 0x7F, 0x00, 0x00] */;

// Парсим:
s8 dx = data[1];  // +127
s8 dy = data[2];  // 0

// Отправляем в Input Core:
input_report_rel(input_dev, REL_X, 127);
input_report_rel(input_dev, REL_Y, 0);
input_sync(input_dev);
```

### Шаг 8: Input Core получает события

Input Core внутри ядра:
```c
void input_event(struct input_dev *dev, unsigned int type,
                 unsigned int code, int value)
{
    // Вызываем всех зарегистрированных Handler'ов
    list_for_each_entry(handle, &dev->h_list, d_node) {
        if (handle->handler->filter) {
            // ЗДЕСЬ ВЫЗЫВАЕТСЯ ТВОЙ filter()!
            if (handle->handler->filter(handle, type, code, value)) {
                return;  // Событие заблокировано
            }
        }
    }

    // Если не заблокировано → передаём в evdev
    evdev_event(dev, type, code, value);
}
```

### Шаг 9: Твой event_filter() вызывается

**ТВОЙ КОД:**

```c
static bool event_filter(struct input_handle *handle, unsigned int type,
                         unsigned int code, int value)
{
    static int dx = 0, dy = 0;

    if (type == EV_REL) {
        if (code == REL_X) {
            dx = value;  // dx = 127
        } else if (code == REL_Y) {
            dy = value;  // dy = 0
        }
        return true;  // ❗ Блокируем событие!
    }

    if (type == EV_SYN && code == SYN_REPORT) {
        // Вычисляем скорость
        ktime_t now = ktime_get();
        s64 time_diff_us = ktime_to_us(ktime_sub(now, driver_data.last_time));

        int distance = abs(dx) + abs(dy);  // 127
        int speed = (int)((s64)distance * 1000000 / time_diff_us);

        // Предположим, time_diff = 10000 мкс (10 мс)
        // speed = 127 * 1000000 / 10000 = 12700 пикс/сек

        // Определяем DPI
        int new_dpi = calculate_dpi(speed);  // speed > 800 → 200%

        if (new_dpi != driver_data.current_dpi) {
            pr_info("mouse_dpi: CHANGE 100%% -> 200%% (speed=%d px/s)\n", speed);
            driver_data.current_dpi = new_dpi;  // 200
        }

        // Масштабируем
        int scaled_dx = (dx * 200) / 100;  // 127 * 2 = 254
        int scaled_dy = (dy * 200) / 100;  // 0

        // Отправляем в ВИРТУАЛЬНУЮ мышь
        input_report_rel(driver_data.virt_mouse, REL_X, 254);
        input_report_rel(driver_data.virt_mouse, REL_Y, 0);
        input_sync(driver_data.virt_mouse);

        // Сбрасываем
        dx = dy = 0;
        driver_data.last_time = now;

        return true;  // ❗ Блокируем оригинальное событие
    }

    return false;
}
```

### Что произошло?

1. **Получили событие:** REL_X = 127 от физической мыши
2. **Заблокировали** его (вернули `true`) → evdev НЕ получит его
3. **Вычислили скорость:** 12700 пикс/сек → быстрое движение
4. **Выбрали DPI:** 200%
5. **Масштабировали:** 127 * 2 = 254
6. **Отправили в виртуальную мышь:** REL_X = 254

### Шаг 10: Виртуальная мышь отправляет событие

Когда ты вызываешь:
```c
input_report_rel(driver_data.virt_mouse, REL_X, 254);
input_sync(driver_data.virt_mouse);
```

Input Core получает событие от ВИРТУАЛЬНОЙ мыши:
- Тип: EV_REL
- Код: REL_X
- Значение: 254

Input Core НЕ вызывает твой `filter()` для виртуальной мыши (потому что она `BUS_VIRTUAL`).

Input Core передаёт событие в **evdev**.

### Шаг 11: evdev создаёт событие в /dev/input/eventX

evdev:
```c
void evdev_event(struct input_dev *dev, unsigned int type,
                 unsigned int code, int value)
{
    struct input_event event;
    event.time = ktime_to_timeval(ktime_get());
    event.type = type;    // EV_REL
    event.code = code;    // REL_X
    event.value = value;  // 254

    // Записываем в очередь для чтения приложениями
    evdev_queue_event(client, &event);
}
```

Событие попадает в `/dev/input/event14` (номер виртуальной мыши).

### Шаг 12: Приложение читает событие

Графический сервер (X11 или Wayland):
```c
int fd = open("/dev/input/event14", O_RDONLY);
while (1) {
    struct input_event ev;
    read(fd, &ev, sizeof(ev));

    if (ev.type == EV_REL && ev.code == REL_X) {
        cursor_x += ev.value;  // cursor_x += 254
        // Перерисовать курсор
    }
}
```

### Шаг 13: Курсор двигается

X11/Wayland двигает курсор на 254 пикселя вправо → видеокарта рисует курсор в новой позиции → ты видишь движение!

### Взаимодействие:

1. **usbhid драйвер:**
   - Обрабатывает USB прерывания
   - Парсит HID отчёты
   - Регистрирует физическую мышь в Input Core
   - Отправляет события (REL_X, REL_Y, BTN_LEFT)

2. **Твой драйвер (Input Handler):**
   - Регистрируется в Input Core
   - Получает КОПИЮ всех событий от физической мыши
   - Блокирует их (return true)
   - Вычисляет скорость, выбирает DPI
   - Масштабирует координаты
   - Отправляет новые события в виртуальную мышь

3. **Виртуальная мышь (driver_data.virt_mouse):**
   - Это `input_dev`, созданный твоим драйвером
   - Ведёт себя как обычная мышь
   - НЕ проходит через твой `filter()` (потому что BUS_VIRTUAL)
   - Передаёт события напрямую в evdev

4. **evdev:**
   - Получает события от виртуальной мыши
   - Создаёт `/dev/input/event14`
   - Приложения читают отсюда

### Почему физическая мышь не доступна приложениям?

Потому что твой `filter()` возвращает `true` → Input Core НЕ передаёт события в evdev для физической мыши.

Если бы ты вернул `false` → были бы ДВЕ мыши:
- `/dev/input/event2` — физическая (100% DPI)
- `/dev/input/event14` — виртуальная (переменный DPI)

И курсор двигался бы в 2 раза быстрее!

## 6.4. Захват устройства (input_grab_device)

В коде есть:
```c
err = input_grab_device(handle);
```

**Что это делает?**

`input_grab_device()` захватывает устройство **эксклюзивно**. Это гарантирует, что ТОЛЬКО твой handler получает события.

Без захвата другие handler'ы (например, другой драйвер) тоже могли бы получать события.

С захватом:
```
Событие от мыши → Input Core → ТОЛЬКО твой filter()
```

Это дополнительная защита от дублирования.

## 6.5. Создание виртуальной мыши

```c
static int create_virtual_mouse(void)
{
    driver_data.virt_mouse = input_allocate_device();

    driver_data.virt_mouse->name = "Virtual Mouse (Accelerated)";
    driver_data.virt_mouse->id.bustype = BUS_VIRTUAL;
    driver_data.virt_mouse->id.vendor = 0x1234;
    driver_data.virt_mouse->id.product = 0x5678;

    // Настраиваем поддерживаемые события
    set_bit(EV_REL, driver_data.virt_mouse->evbit);
    set_bit(REL_X, driver_data.virt_mouse->relbit);
    set_bit(REL_Y, driver_data.virt_mouse->relbit);
    set_bit(REL_WHEEL, driver_data.virt_mouse->relbit);

    set_bit(EV_KEY, driver_data.virt_mouse->evbit);
    set_bit(BTN_LEFT, driver_data.virt_mouse->keybit);
    set_bit(BTN_RIGHT, driver_data.virt_mouse->keybit);
    set_bit(BTN_MIDDLE, driver_data.virt_mouse->keybit);

    return input_register_device(driver_data.virt_mouse);
}
```

### Что происходит?

1. **input_allocate_device()** — выделяет память под `input_dev`
2. **Заполняем поля:**
   - `name` — имя устройства (видно в `/proc/bus/input/devices`)
   - `bustype = BUS_VIRTUAL` — это виртуальное устройство (не USB, не PS/2)
   - `vendor/product` — произвольные ID
3. **set_bit()** — устанавливаем флаги поддерживаемых событий:
   - `evbit` — типы событий (EV_REL, EV_KEY)
   - `relbit` — относительные оси (REL_X, REL_Y, REL_WHEEL)
   - `keybit` — кнопки (BTN_LEFT, BTN_RIGHT, BTN_MIDDLE)
4. **input_register_device()** — регистрируем в Input Core

После регистрации:
- Input Core создаёт `/dev/input/eventX` через evdev
- Приложения могут читать события

### Почему BUS_VIRTUAL?

Это говорит Input Core: "Это не настоящее физическое устройство".

В твоём `mouse_connect()` есть проверка:
```c
if (dev->id.bustype == BUS_VIRTUAL)
    return -ENODEV;
```

Это предотвращает зацикливание: твой handler НЕ подключается к виртуальной мыши!

Иначе:
```
Виртуальная мышь → событие → твой filter() →
    масштабирует → отправляет в виртуальную мышь →
        событие → твой filter() → ЗАЦИКЛИВАНИЕ!
```

# 7. Взаимодействие с другими драйверами

## 7.1. Device Stack (стек устройств)

В Windows есть концепция **Device Stack** — стопка драйверов для одного устройства.

```
┌──────────────────┐
│ Драйвер фильтр   │
├──────────────────┤
│ Функциональный   │
│ драйвер          │
├──────────────────┤
│ Драйвер шины     │
└──────────────────┘
```

В Linux это работает иначе, но **похожая идея**:

```
Приложение
    ↓
evdev (event handler)
    ↓
Input Core
    ↓
┌────────────────┬──────────────┐
│ ТВОЙ Handler   │  usbhid      │
│ (фильтр)       │  (функцио-   │
│                │   нальный)   │
└────────────────┴──────────────┘
    ↓                   ↓
Виртуальная мышь   USB драйвер
                        ↓
                   USB контроллер
                        ↓
                   Физическая мышь
```

**Твой драйвер — это фильтр**, который сидит между Input Core и приложениями.

## 7.2. Загрузка модулей: зависимости

Когда ты загружаешь свой модуль:
```bash
sudo insmod mouse_accel.ko
```

Ядро проверяет зависимости:
- Твой модуль использует символы из **input-core** (input_register_handler, input_allocate_device)
- input-core уже загружен (встроен в ядро)

Если бы input-core был модулем, ядро сначала загрузило бы его.

## 7.3. Конкуренция за мышь

Что если есть другой драйвер, который тоже хочет перехватывать мышь?

**В Linux:**
- Несколько Input Handler'ов могут зарегистрироваться
- Все получают КОПИЮ событий
- Каждый может заблокировать событие (return true)

Если два handler'а вернут `true` — событие всё равно заблокировано.

**В твоём случае:**
- usbhid регистрирует мышь
- Твой handler подключается через `connect()`
- Ты захватываешь через `input_grab_device()` → эксклюзивный доступ

## 7.4. Автозагрузка: модули ядра

### Как работает автозагрузка?

Файл `/etc/modules-load.d/mouse_dpi.conf`:
```
mouse_accel
```

При загрузке системы:
1. **systemd-modules-load.service** запускается
2. Читает файлы из `/etc/modules-load.d/`
3. Для каждого модуля вызывает `modprobe mouse_accel`
4. `modprobe` ищет модуль в `/lib/modules/$(uname -r)/`
5. Загружает модуль через `finit_module()` syscall
6. Ядро вызывает `mouse_accel_init()`

### Что происходит в mouse_accel_init()?

```c
static int __init mouse_accel_init(void)
{
    // 1. Инициализация структуры
    memset(&driver_data, 0, sizeof(driver_data));
    driver_data.current_dpi = 100;
    driver_data.last_time = ktime_get();

    // 2. Создаём виртуальную мышь
    create_virtual_mouse();

    // 3. Регистрируем Input Handler
    input_register_handler(&mouse_handler);

    return 0;
}
```

После этого:
- Виртуальная мышь создана → `/dev/input/eventX` появился
- Handler зарегистрирован → Input Core знает о нём

Если мышь уже подключена:
- Input Core вызывает `mouse_connect()` для каждой существующей мыши
- Твой драйвер подключается к ним

Если мышь подключится позже (PnP):
- USB драйвер обнаружит её → зарегистрирует в Input Core
- Input Core → "Есть новая мышь, проверю всех handler'ов"
- Input Core вызовет твой `mouse_connect()`

# Итоговая картина: всё вместе

## Полный путь от физического движения до курсора:

```
1. Физическое движение мыши на 1 см вправо
         ↓
2. Оптический сенсор: +127 единиц
         ↓
3. Микроконтроллер мыши → HID отчёт [0x00, 0x7F, 0x00, 0x00]
         ↓
4. USB передача → USB контроллер (DMA в память)
         ↓
5. USB контроллер → Прерывание (IRQ 16)
         ↓
6. CPU → Обработчик прерывания → usbhid драйвер
         ↓
7. usbhid парсит HID → REL_X=127, REL_Y=0
         ↓
8. usbhid → input_report_rel() → Input Core
         ↓
9. Input Core → Вызывает всех Handler'ов
         ↓
10. ТВОЙ event_filter():
    - Получает REL_X=127
    - Блокирует событие (return true)
    - Вычисляет скорость: 12700 пикс/сек
    - Выбирает DPI: 200%
    - Масштабирует: 127 * 2 = 254
    - Отправляет в виртуальную мышь: REL_X=254
         ↓
11. Виртуальная мышь → input_report_rel() → Input Core
         ↓
12. Input Core → evdev (для виртуальной мыши)
         ↓
13. evdev → /dev/input/event14
         ↓
14. X11/Wayland → read() → получает REL_X=254
         ↓
15. X11 → cursor_x += 254
         ↓
16. Видеокарта → рисует курсор в новой позиции
         ↓
17. ТЫ ВИДИШЬ ДВИЖЕНИЕ!
```

## Используемые технологии в твоём драйвере:

✅ **Драйверы** — твой код это драйвер-фильтр
