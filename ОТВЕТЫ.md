## 15. Что такое WDF и чем отличаются KMDF и UMDF?


 


**WDF (Windows Driver Framework)** - это современная упрощенная модель программирования драйверов для Windows, представляющая собой надстройку над WDM (Windows Driver Model).


 


![Сравнение технологий драйверов](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_5.png)


 


### Теоретическое пояснение:


 


**WDF** состоит из двух основных фреймворков:


 


1. **KMDF (Kernel-Mode Driver Framework)** - фреймворк для разработки драйверов режима ядра:


   - Работает в адресном пространстве ядра (Ring 0)


   - Имеет прямой доступ ко всему оборудованию


   - Критичен к ошибкам (сбой может привести к BSOD)


   - Используется для драйверов, требующих высокой производительности


   - Примеры: драйверы файловых систем, сетевых адаптеров


 


2. **UMDF (User-Mode Driver Framework)** - фреймворк для разработки драйверов пользовательского режима:


   - Работает в адресном пространстве пользователя (Ring 3)


   - Изолирован от ядра через специальный механизм (Reflector)


   - Сбой драйвера не приводит к краху системы


   - Проще в отладке и разработке


   - Примеры: драйверы принтеров, сканеров, некоторых USB-устройств


 


**Ключевые различия:**


- **Безопасность**: UMDF безопаснее (изолирован от ядра)


- **Производительность**: KMDF быстрее (прямой доступ)


- **Отладка**: UMDF проще отлаживать


- **Стабильность системы**: ошибка в UMDF не приводит к BSOD

## 16. Опишите структуру DRIVER_OBJECT и её основные поля


 


Структура DRIVER_OBJECT является фундаментальной для любого драйвера Windows. Она создается системой при загрузке драйвера.


 


![DRIVER_OBJECT в контексте](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_15.png)


 


![Таблица диспетчеризации IRP](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_16.png)


 


![Структура DRIVER_OBJECT](extracted_images/4.СПО_Структура KMDF-драйвера_page_4.png)


 


### Теоретическое пояснение:


 


Структура **DRIVER_OBJECT** содержит:


 


```c


typedef struct _DRIVER_OBJECT {


    CSHORT Type;                    // Тип объекта


    CSHORT Size;                    // Размер структуры


    PDEVICE_OBJECT DeviceObject;    // Указатель на первое устройство


    ULONG Flags;                    // Флаги драйвера


    PVOID DriverStart;              // Адрес начала драйвера в памяти


    ULONG DriverSize;               // Размер драйвера


    PVOID DriverSection;            // Секция драйвера


    PDRIVER_EXTENSION DriverExtension; // Расширение драйвера


    UNICODE_STRING DriverName;      // Имя драйвера


    PUNICODE_STRING HardwareDatabase; // База данных оборудования


    PFAST_IO_DISPATCH FastIoDispatch; // Быстрый ввод-вывод


    PDRIVER_INITIALIZE DriverInit;  // Точка входа DriverEntry


    PDRIVER_STARTIO DriverStartIo;  // Функция StartIo


    PDRIVER_UNLOAD DriverUnload;    // Функция выгрузки


    PDRIVER_DISPATCH MajorFunction[IRP_MJ_MAXIMUM_FUNCTION + 1]; // Таблица диспетчеризации


};


```


 


**Основные поля:**


 


1. **DeviceObject** - указатель на связанный список всех устройств, созданных драйвером


2. **DriverName** - полное имя драйвера в реестре


3. **DriverUnload** - указатель на функцию выгрузки драйвера


4. **MajorFunction[]** - массив указателей на функции-обработчики IRP (таблица диспетчеризации)


   - Содержит 28 элементов (IRP_MJ_CREATE, IRP_MJ_READ, IRP_MJ_WRITE и т.д.)


   - Каждый элемент указывает на функцию обработки соответствующего типа запроса


 


Эта структура является "визитной карточкой" драйвера в системе и управляет всеми его устройствами и обработчиками запросов.

В KMDF-драйвере существуют три основные обязательные функции:


 


![Функция DriverEntry](extracted_images/4.СПО_Структура KMDF-драйвера_page_7.png)


 


![Функция Unload](extracted_images/4.СПО_Структура KMDF-драйвера_page_8.png)


 


![Функция AddDevice](extracted_images/4.СПО_Структура KMDF-драйвера_page_9.png)

### Теоретическое пояснение:


 


**1. DriverEntry** - точка входа драйвера:


```c


NTSTATUS DriverEntry(


    PDRIVER_OBJECT DriverObject,


    PUNICODE_STRING RegistryPath


);


```


- Вызывается системой при загрузке драйвера


- Инициализирует структуру DRIVER_OBJECT


- Регистрирует обработчики IRP в таблице MajorFunction[]


- Регистрирует функции AddDevice и Unload


- Возвращает STATUS_SUCCESS при успехе


 


**2. AddDevice** - создание объекта устройства:


```c


NTSTATUS AddDevice(


    PDRIVER_OBJECT DriverObject,

);


```


- Вызывается PnP-менеджером при обнаружении нового устройства


- Создает функциональный объект устройства (FDO)

```c


VOID Unload(


    PDRIVER_OBJECT DriverObject


);


```


- Вызывается при выгрузке драйвера из системы


- Освобождает все выделенные ресурсы


- Удаляет все объекты устройств


- Отменяет регистрацию обработчиков


 


Без этих трех функций драйвер не сможет корректно загрузиться, работать с устройствами и выгрузиться из системы.

## 18. Что такое IRP и как он обрабатывается в стеке устройств?


 


**IRP (I/O Request Packet)** - это пакет запроса ввода-вывода, основная структура данных для передачи запросов между драйверами в Windows.


 


![IRP в стеке устройств](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_12.png)


 


![Пример обработки IRP для USB](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_13.png)


 


![Подробная схема обработки IRP](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_14.png)


 


![Диспетчеризация IRP](extracted_images/4.СПО_Структура KMDF-драйвера_page_12.png)


 


### Теоретическое пояснение:


 


**IRP (I/O Request Packet)** - это структура данных, которая:


- Содержит всю информацию о запросе ввода-вывода


- Передается по стеку драйверов от верхнего уровня к нижнему


- Может обрабатываться асинхронно


 


**Обработка IRP в стеке устройств:**


 


1. **Создание IRP**: Приложение вызывает API (например, ReadFile), менеджер ввода-вывода создает IRP


 


2. **Передача вниз по стеку**:


   - IRP передается верхнему драйверу в стеке (filter driver или FDO)


   - Каждый драйвер может:


     - **Обработать и завершить** IRP (IoCompleteRequest)


     - **Передать ниже** без изменений (IoCallDriver)


     - **Модифицировать** и передать ниже


     - **Создать новые IRP** на основе текущего


 


3. **Достижение нижнего уровня**:


   - PDO (Physical Device Object) получает IRP


   - Взаимодействует с физическим устройством


 


4. **Завершение (Completion)**:


   - После обработки IRP завершается (IoCompleteRequest)


   - Вызываются completion routines в обратном порядке (снизу вверх)


   - Результат возвращается приложению


 


**Пример** (USB-накопитель):


- Приложение → IRP_MJ_READ → File System Driver → Volume Manager → USB Storage Class Driver → USB Hub Driver → USB Host Controller → Устройство


 


Каждый драйвер в цепочке выполняет свою часть работы, трансформируя высокоуровневый запрос в низкоуровневые команды устройству.

## 19. Как выглядит структура IRP и какие поля в ней наиболее важны?


 


Структура IRP (I/O Request Packet) является ключевой для понимания работы подсистемы ввода-вывода Windows.


 


![Структура IRP](extracted_images/4.СПО_Структура KMDF-драйвера_page_14.png)


 


![Структура IRP продолжение](extracted_images/4.СПО_Структура KMDF-драйвера_page_15.png)


 


![Типы IRP](extracted_images/4.СПО_Структура KMDF-драйвера_page_16.png)


 


### Теоретическое пояснение:


 


Структура **IRP** содержит:


 


```c


typedef struct _IRP {


    CSHORT Type;              // Тип структуры


    USHORT Size;              // Размер IRP


    PMDL MdlAddress;          // Описатель списка памяти (для DMA)


    ULONG Flags;              // Флаги IRP


    PIRP AssociatedIrp;       // Связанные IRP


    IO_STATUS_BLOCK IoStatus; // Блок статуса операции


    KPROCESSOR_MODE RequestorMode; // Режим запросившего процесса


    BOOLEAN PendingReturned;  // Флаг отложенного выполнения


    CHAR StackCount;          // Количество стеков


    CHAR CurrentLocation;     // Текущая позиция в стеке


    BOOLEAN Cancel;           // Флаг отмены


    KIRQL CancelIrql;         // IRQL для отмены


    PDRIVER_CANCEL CancelRoutine; // Функция отмены


    PVOID UserBuffer;         // Буфер пользователя


    // ... другие поля


    PIO_STACK_LOCATION Tail.Overlay.CurrentStackLocation; // Текущий стек


};


```


 


**Наиболее важные поля:**


 


1. **IoStatus** - блок статуса ввода-вывода:


   - Status: код завершения операции (STATUS_SUCCESS, STATUS_PENDING и т.д.)


   - Information: количество переданных байт или другая информация


 


2. **MdlAddress** - Memory Descriptor List:


   - Используется для DMA-операций


   - Описывает физические страницы памяти буфера


 


3. **CurrentStackLocation** - указатель на текущий IO_STACK_LOCATION:


   - Содержит параметры для текущего драйвера


   - MajorFunction: тип операции (IRP_MJ_READ, IRP_MJ_WRITE и т.д.)


   - MinorFunction: подтип операции


   - Parameters: специфичные параметры (смещение, длина для чтения/записи)


 


4. **UserBuffer** - буфер данных:


   - Адрес буфера в пространстве пользователя


   - Используется для передачи данных


 


5. **Flags** - флаги операции:


   - IRP_BUFFERED_IO: буферизованный ввод-вывод


   - IRP_PAGING_IO: операция подкачки страниц


   - IRP_SYNCHRONOUS_API: синхронная операция


 


6. **Cancel** и **CancelRoutine**:


   - Для поддержки отмены операций


   - Важно для длительных операций


 


**Типы IRP (MajorFunction):**


- IRP_MJ_CREATE - открытие устройства


- IRP_MJ_CLOSE - закрытие


- IRP_MJ_READ - чтение


- IRP_MJ_WRITE - запись


- IRP_MJ_DEVICE_CONTROL - управляющие команды (IOCTL)


- IRP_MJ_PNP - Plug and Play операции


- IRP_MJ_POWER - управление питанием


- И другие (всего 28 типов)

## 20. Что такое PnP-дерево и как формируется стек устройств?


 


**PnP (Plug and Play)** - технология автоматического обнаружения и настройки устройств в Windows.


 


![PnP-дерево устройств](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_8.png)


 


![Структура PnP-дерева](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_9.png)


 


![Формирование стека устройств](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_10.png)


 


![Стек устройств с PDO и FDO](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_11.png)


 


### Теоретическое пояснение:


 


**PnP-дерево (Device Tree)** - иерархическая структура всех устройств в системе:


 


- **Корень дерева**: системная плата (motherboard)


- **Узлы**: шины и устройства (PCI, USB, ACPI)


- **Листья**: конечные устройства (мышь, клавиатура, диск)


 


Каждое устройство представлено **узлом устройства (devnode)**, который содержит информацию о:


- Идентификаторе устройства (Hardware ID)


- Драйверах


- Ресурсах (IRQ, порты ввода-вывода, память)


- Состоянии устройства


 


**Формирование стека устройств:**


 


1. **Bus Driver** (драйвер шины) обнаруживает дочернее устройство


 


2. **Создание PDO** (Physical Device Object):


   - Bus Driver создает PDO для устройства


   - PDO представляет физическое устройство


   - PDO - основа стека, всегда внизу


 


3. **PnP Manager** находит подходящий драйвер через INF-файл


 


4. **Создание FDO** (Functional Device Object):


   - Function Driver создает FDO


   - FDO прикрепляется к PDO через IoAttachDeviceToDeviceStack


   - FDO управляет функциональностью устройства


 


5. **Добавление Filter Drivers** (опционально):


   - Upper Filter - над FDO (модифицирует запросы до FDO)


   - Lower Filter - между FDO и PDO (модифицирует после FDO)


 


**Структура стека (сверху вниз):**


```


┌─────────────────────┐


│ Upper Filter DO     │ (опционально)


├─────────────────────┤


│ FDO                 │ (Function Driver)


├─────────────────────┤


│ Lower Filter DO     │ (опционально)


├─────────────────────┤


│ PDO                 │ (Bus Driver)


└─────────────────────┘


```


 


**Пример** (USB-мышь):


- USB Root Hub (PDO, создан PCI Bus Driver)


- USB Hub (FDO + новый Bus Driver)


- USB Mouse (PDO, создан USB Hub)


- HID Class Driver (FDO)


- Mouse Class Driver (Filter)


 


IRP проходят через весь стек сверху вниз, позволяя каждому драйверу внести свой вклад в обработку.

## 21. Какова роль функции DriverEntry в драйвере?


 


Функция **DriverEntry** является точкой входа для любого драйвера Windows.


 


![Функция DriverEntry](extracted_images/4.СПО_Структура KMDF-драйвера_page_7.png)


 


![Пример реализации DriverEntry](extracted_images/4.СПО_Структура KMDF-драйвера_page_10.png)


 


![Таблица диспетчеризации](extracted_images/4.СПО_Структура KMDF-драйвера_page_11.png)


 


### Теоретическое пояснение:


 


**DriverEntry** - первая функция, вызываемая при загрузке драйвера в систему.


 


**Сигнатура:**


```c


NTSTATUS DriverEntry(


    PDRIVER_OBJECT DriverObject,


    PUNICODE_STRING RegistryPath


);


```


 


**Параметры:**


- **DriverObject** - указатель на объект драйвера, созданный системой


- **RegistryPath** - путь к параметрам драйвера в реестре (например, `\Registry\Machine\System\CurrentControlSet\Services\MyDriver`)


 


**Основные задачи DriverEntry:**


 


1. **Инициализация структуры DRIVER_OBJECT:**


   ```c


   DriverObject->DriverUnload = UnloadDriver;


   DriverObject->DriverExtension->AddDevice = AddDevice;


   ```


 


2. **Регистрация обработчиков IRP** (заполнение таблицы диспетчеризации):


   ```c


   DriverObject->MajorFunction[IRP_MJ_CREATE] = DispatchCreate;


   DriverObject->MajorFunction[IRP_MJ_CLOSE] = DispatchClose;


   DriverObject->MajorFunction[IRP_MJ_READ] = DispatchRead;


   DriverObject->MajorFunction[IRP_MJ_WRITE] = DispatchWrite;


   DriverObject->MajorFunction[IRP_MJ_DEVICE_CONTROL] = DispatchDeviceControl;


   DriverObject->MajorFunction[IRP_MJ_PNP] = DispatchPnP;


   DriverObject->MajorFunction[IRP_MJ_POWER] = DispatchPower;


   ```


 


3. **Инициализация глобальных структур данных драйвера**:


   - Создание списков


   - Инициализация блокировок (spinlocks, mutexes)


   - Выделение памяти для общих структур


 


4. **Чтение параметров из реестра** (через RegistryPath):


   - Конфигурационные параметры


   - Настройки оборудования


 


5. **Создание символических ссылок** (для драйверов, не использующих PnP):


   ```c


   IoCreateSymbolicLink(&DosDeviceName, &DeviceName);


   ```


 


**Возвращаемое значение:**


- **STATUS_SUCCESS** - драйвер успешно загружен


- **STATUS_UNSUCCESSFUL** или другой код ошибки - драйвер будет выгружен


 


**Важно:**


- DriverEntry выполняется в контексте системного процесса


- При ошибке в DriverEntry драйвер немедленно выгружается


- Вся инициализация должна быть выполнена в DriverEntry


- Долгие операции нужно отложить на потом (например, в AddDevice)


 


Без корректной DriverEntry драйвер не сможет зарегистрироваться в системе и обрабатывать запросы.

## 22. Что такое PDO и FDO в контексте стека устройств?


 


**PDO (Physical Device Object)** и **FDO (Functional Device Object)** - ключевые компоненты архитектуры PnP в Windows.


 


![PDO и FDO в стеке](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_10.png)


 


![Взаимодействие PDO и FDO](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_11.png)


 


![Реализация PnP узла](extracted_images/4.СПО_Структура KMDF-драйвера_page_3.png)


 


### Теоретическое пояснение:


 


**PDO (Physical Device Object)** - физический объект устройства:


 


**Создается:** Bus Driver (драйвером шины)


**Представляет:** Физическое устройство или слот на шине


**Роль:**


- Основа стека устройства (всегда внизу)


- Содержит информацию об устройстве (VID, PID, Hardware ID)


- Обрабатывает специфичные для шины операции


- Управляет ресурсами устройства (IRQ, DMA, порты)


 


**Пример:**


- USB Controller создает PDO для каждого USB-устройства


- PCI Bus Driver создает PDO для каждого PCI-устройства


 


**FDO (Functional Device Object)** - функциональный объект устройства:


 


**Создается:** Function Driver (функциональным драйвером)


**Представляет:** Функциональность устройства


**Роль:**


- Прикрепляется поверх PDO


- Управляет основной функциональностью устройства


- Обрабатывает высокоуровневые запросы ввода-вывода


- Может создавать собственные PDO (если выступает как Bus Driver)


 


**Пример:**


- Драйвер USB Mass Storage создает FDO для флешки


- Драйвер сетевой карты создает FDO для Ethernet адаптера


 


**Взаимодействие в стеке:**


 


```


Приложение: ReadFile()


     ↓


[Upper Filter DO] - фильтрация "сверху" (опционально)


     ↓


[FDO] ← Function Driver - основная функциональность


     ↓


[Lower Filter DO] - фильтрация "снизу" (опционально)


     ↓


[PDO] ← Bus Driver - взаимодействие с шиной


     ↓


Оборудование


```


 


**Ключевые различия:**


 


| Характеристика | PDO | FDO |


|----------------|-----|-----|


| Создатель | Bus Driver | Function Driver |


| Позиция | Низ стека | Поверх PDO |


| Функция | Интерфейс к шине | Функциональность устройства |


| PnP | Обязателен | Обязателен для PnP-устройств |


| Ресурсы | Запрашивает у PnP Manager | Использует выделенные ресурсы |


 


**Пример (USB Flash Drive):**


1. **PDO**: создан USB Hub Driver, представляет USB-устройство на шине


2. **FDO**: создан USB Mass Storage Driver, управляет функциональностью накопителя


3. Дополнительно USB Mass Storage может создать новый PDO для раздела, к которому подключится файловая система (ещё один FDO)


 


Такая архитектура позволяет разделить ответственность: Bus Driver знает о шине, Function Driver - об устройстве, не заботясь о деталях шины.

## 23. Чем отличается архитектура UMDF от KMDF?


 


**UMDF (User-Mode Driver Framework)** имеет принципиально иную архитектуру по сравнению с **KMDF (Kernel-Mode Driver Framework)**.


 


![Размещение KMDF](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_6.png)


 


![Размещение UMDF](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_7.png)


 


![Инфраструктура UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_4.png)


 


![Компоненты UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_5.png)


 


### Теоретическое пояснение:


 


**Архитектурные различия:**


 


**KMDF (Kernel-Mode):**


- Драйвер работает в режиме ядра (Ring 0)


- Прямой доступ к оборудованию


- Минимальные накладные расходы


- Высокая производительность


- Ошибка приводит к BSOD


- Сложная отладка


 


**UMDF (User-Mode):**


- Драйвер работает в пользовательском режиме (Ring 3)


- Доступ к оборудованию через посредников


- Дополнительные компоненты инфраструктуры


- Некоторые накладные расходы на переключение контекста


- Ошибка не влияет на стабильность системы


- Простая отладка (как обычное приложение)


 


**Инфраструктура UMDF:**


 


1. **Reflector (Отражатель)** - драйвер режима ядра:


   - Единый для всех UMDF-драйверов (WUDFRd.sys)


   - Находится в стеке устройств


   - Перенаправляет IRP из ядра в пользовательский режим


   - Обеспечивает связь между ядром и Host Process


 


2. **Host Process (Хост-процесс)** - WUDFHost.exe:


   - Изолированный процесс пользовательского режима


   - Содержит один или несколько UMDF-драйверов


   - Содержит экземпляры UMDF Framework


   - При сбое перезапускается Driver Manager'ом


 


3. **Driver Manager (Менеджер драйверов)** - служба Windows:


   - Управляет Host Process'ами


   - Создает и контролирует процессы для драйверов


   - Перезапускает упавшие процессы


   - Обеспечивает изоляцию драйверов


 


4. **UMDF Framework** (библиотеки):


   - WUDFx.dll - основной фреймворк


   - Предоставляет объектную модель (COM-based)


   - Абстрагирует низкоуровневые детали


 


**Поток запроса в UMDF:**


 


```


Приложение


    ↓ (System Call)


Kernel I/O Manager


    ↓ (IRP)


Reflector (WUDFRd.sys) ← ядро


    ↓ (ALPC/LPC)


Driver Manager


    ↓


Host Process (WUDFHost.exe) ← пользовательский режим


    ↓


UMDF Framework (WUDFx.dll)


    ↓


Ваш UMDF-драйвер (YourDriver.dll)


```


 


**Ключевые отличия:**


 


| Аспект | KMDF | UMDF |


|--------|------|------|


| Режим выполнения | Kernel Mode (Ring 0) | User Mode (Ring 3) |


| Файл драйвера | .sys | .dll |


| Доступ к памяти | Вся физическая память | Только своё адресное пространство |


| Сбой драйвера | BSOD | Перезапуск процесса |


| Отладка | Kernel debugger | User-mode debugger (WinDbg, VS) |


| Производительность | Максимальная | Ниже из-за переключений контекста |


| Технология | C, WDM API | COM, C++ |


| Изоляция | Нет | Полная изоляция процессов |


 


**Когда использовать:**


- **KMDF**: высокопроизводительные устройства (сеть, storage, видео)


- **UMDF**: периферия (принтеры, сканеры, простые USB-устройства)

## 24. Какие компоненты входят в инфраструктуру UMDF-драйвера?


 


Инфраструктура UMDF состоит из нескольких взаимосвязанных компонентов, обеспечивающих работу драйверов в пользовательском режиме.


 


![Инфраструктура UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_4.png)


 


![Описание компонентов UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_5.png)


 


![Использование COM в UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_3.png)


 


![Компоненты Host Process](extracted_images/5.СПО_Структура UMDF-драйвера_page_10.png)


 


### Теоретическое пояснение:


 


**Основные компоненты инфраструктуры UMDF:**


 


**1. Reflector (WUDFRd.sys)** - драйвер-отражатель режима ядра:


 


**Роль:**


- Единственный компонент UMDF в режиме ядра


- Общий для всех UMDF-драйверов в системе


- Входит в стек устройства как верхний фильтр


 


**Функции:**


- Принимает IRP от I/O Manager


- Преобразует IRP в сообщения для пользовательского режима


- Передает запросы в Driver Manager через ALPC (Advanced Local Procedure Call)


- Возвращает результаты обратно в ядро


- Обеспечивает безопасность и изоляцию


 


**2. Driver Manager** - служба управления драйверами:


 


**Роль:**


- Служба Windows (WUDFSvc)


- Центральный координатор UMDF-драйверов


 


**Функции:**


- Создает и управляет Host Process'ами


- Загружает UMDF-драйверы в соответствующие процессы


- Мониторит состояние процессов


- Перезапускает упавшие Host Process'ы


- Управляет жизненным циклом драйверов


- Обеспечивает изоляцию между разными драйверами


 


**3. Host Process (WUDFHost.exe)** - процесс-хост:


 


**Роль:**


- Изолированный процесс пользовательского режима


- Контейнер для одного или нескольких UMDF-драйверов


 


**Содержимое:**


- Экземпляры UMDF-драйверов (.dll)


- UMDF Framework (WUDFx.dll)


- Runtime библиотеки


 


**Характеристики:**


- Работает под учетной записью LocalService (ограниченные права)


- Каждый процесс может содержать несколько драйверов


- При сбое перезапускается без влияния на систему


- Изолирован от других процессов


 


**4. UMDF Framework** - библиотеки фреймворка:


 


**Компоненты:**


- **WUDFx.dll** - основная библиотека фреймворка


- **WUDFPlatform.dll** - платформенный слой


 


**Функции:**


- Предоставляет COM-интерфейсы для драйвера:


  - IWDFDriver - драйвер


  - IWDFDevice - устройство


  - IWDFIoQueue - очередь запросов


  - IWDFIoRequest - запрос ввода-вывода


- Управляет объектами драйвера


- Обрабатывает синхронизацию


- Предоставляет утилиты и вспомогательные функции


 


**5. UMDF Driver (Ваш драйвер)** - .dll файл:


 


**Структура:**


- DLL с экспортируемыми функциями


- Реализует COM-интерфейсы:


  - IDriverEntry


  - Callback-интерфейсы


- Бизнес-логика управления устройством


 


**Взаимодействие компонентов:**


 


```


┌─────────────────────────────────────┐


│         Kernel Mode                 │


│                                     │


│  I/O Manager → Reflector (WUDFRd)  │


└──────────────┬──────────────────────┘


               │ ALPC


┌──────────────┴──────────────────────┐


│         User Mode                   │


│  ┌──────────────────────────────┐   │


│  │   Driver Manager (WUDFSvc)   │   │


│  └──────────┬───────────────────┘   │


│             │                        │


│  ┌──────────┴───────────────────┐   │


│  │  Host Process (WUDFHost.exe) │   │


│  │  ┌────────────────────────┐  │   │


│  │  │ UMDF Framework         │  │   │


│  │  │ (WUDFx.dll)           │  │   │


│  │  ├────────────────────────┤  │   │


│  │  │ Your Driver (*.dll)    │  │   │


│  │  └────────────────────────┘  │   │


│  └──────────────────────────────┘   │


└─────────────────────────────────────┘


```


 


**Дополнительные компоненты:**


 


- **UMDF Redistributable** - распространяемый пакет UMDF


- **UMDF Class Extensions** - расширения для классов устройств (HID, USB и т.д.)


- **Tracing/Logging** - компоненты трассировки (WPP, ETW)


 


**Преимущества архитектуры:**


- Изоляция: сбой одного драйвера не влияет на другие


- Безопасность: драйверы работают с минимальными привилегиями


- Отказоустойчивость: автоматический перезапуск упавших процессов


- Отладка: стандартные инструменты пользовательского режима

## 25. Опишите порядок обработки запроса ввода-вывода в UMDF


 


Обработка запросов ввода-вывода в UMDF проходит через несколько уровней и компонентов.


 


![Порядок обработки I/O в UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_7.png)


 


![Детальное описание обработки](extracted_images/5.СПО_Структура UMDF-драйвера_page_8.png)


 


![Продолжение описания](extracted_images/5.СПО_Структура UMDF-драйвера_page_9.png)


 


### Теоретическое пояснение:


 


**Полный цикл обработки I/O запроса в UMDF:**


 


**Шаг 1: Создание запроса приложением**


- Приложение вызывает API (ReadFile, WriteFile, DeviceIoControl)


- Запрос переходит в пространство ядра через системный вызов


 


**Шаг 2: I/O Manager создает IRP**


- Kernel I/O Manager формирует IRP (I/O Request Packet)


- IRP содержит всю информацию о запросе


 


**Шаг 3: IRP передается в стек устройства**


- IRP проходит через драйверы-фильтры (если есть)


- Достигает Reflector (WUDFRd.sys)


 


**Шаг 4: Reflector перехватывает IRP**


- WUDFRd.sys получает IRP в режиме ядра


- Преобразует IRP в специальный формат сообщения


- Маршалит (marshaling) данные для передачи в пользовательский режим


 


**Шаг 5: Передача в Driver Manager**


- Reflector отправляет сообщение через ALPC (Advanced Local Procedure Call)


- Driver Manager получает запрос


 


**Шаг 6: Driver Manager передает в Host Process**


- Определяет, какому Host Process принадлежит устройство


- Пересылает запрос соответствующему WUDFHost.exe


 


**Шаг 7: Host Process получает запрос**


- WUDFHost.exe принимает сообщение


- Передает его в UMDF Framework


 


**Шаг 8: UMDF Framework обрабатывает запрос**


- WUDFx.dll создает объект IWDFIoRequest


- Определяет целевое устройство (IWDFDevice)


- Находит соответствующую очередь (IWDFIoQueue)


 


**Шаг 9: Запрос помещается в очередь**


- Framework помещает запрос в очередь ввода-вывода


- Очередь может быть:


  - Sequential (последовательная) - по одному запросу


  - Parallel (параллельная) - несколько одновременно


  - Manual (ручная) - драйвер сам извлекает


 


**Шаг 10: Вызов callback-функции драйвера**


- Framework вызывает соответствующий callback:


  - OnRead() для чтения


  - OnWrite() для записи


  - OnDeviceIoControl() для IOCTL


- Драйвер получает интерфейс IWDFIoRequest


 


**Шаг 11: Драйвер обрабатывает запрос**


- Извлекает параметры из IWDFIoRequest


- Получает буферы данных (GetInputMemory/GetOutputMemory)


- Выполняет операцию с устройством:


  - Может отправить запрос на нижестоящий драйвер (ForwardToIoQueue)


  - Может взаимодействовать с оборудованием через Reflector


  - Может выполнить операцию полностью в пользовательском режиме


 


**Шаг 12: Завершение запроса**


- Драйвер вызывает IWDFIoRequest::Complete(status)


- Указывает статус выполнения и количество обработанных байт


 


**Шаг 13: Framework возвращает результат**


- UMDF Framework формирует ответное сообщение


- Отправляет результат обратно через Driver Manager


 


**Шаг 14: Результат передается в Reflector**


- Driver Manager → Reflector через ALPC


- Данные демаршалятся (unmarshaling)


 


**Шаг 15: Reflector завершает IRP**


- WUDFRd.sys получает результат


- Вызывает IoCompleteRequest для исходного IRP


- Устанавливает статус и количество байт


 


**Шаг 16: Результат возвращается приложению**


- IRP проходит обратно через стек устройства


- I/O Manager возвращает результат приложению


- Приложение получает данные и код возврата


 


**Схема потока:**


```


[App] →(1)→ [API] →(2)→ [Kernel I/O Mgr] →(3)→ [Reflector]


                                                    ↓(4)


                                            [Driver Manager]


                                                    ↓(5)


                                             [Host Process]


                                                    ↓(6)


                                            [UMDF Framework]


                                                    ↓(7)


                                            [Your Driver Code]


                                                    ↓(8)


                                            [Complete Request]


                                                    ↓(9)


[App] ←(16)← [API] ←(15)← [I/O Mgr] ←(14)← [Reflector]


```


 


**Важные моменты:**


 


- **Асинхронность**: запрос может быть отложен (pended) на любом этапе


- **Отмена**: приложение может отменить запрос (IRP_MJ_CANCEL)


- **Таймауты**: система контролирует время обработки


- **Буферизация**: данные копируются между ядром и пользовательским режимом


- **Производительность**: множественные переключения контекста - причина более низкой производительности по сравнению с KMDF

## 26. Какие функции являются обязательными для UMDF-драйвера?


 


UMDF-драйвер должен реализовать определенный набор функций и интерфейсов для корректной работы.


 


![Функция DllMain](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_3.png)


 


![Функция DllGetClassObject](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_4.png)


 


![Интерфейс IDriverEntry](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_5.png)


 


![Интерфейс IWDFDriver](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_6.png)


 


### Теоретическое пояснение:


 


**Обязательные функции и интерфейсы UMDF-драйвера:**


 


**1. DllMain** - точка входа DLL:


 


```c


BOOL WINAPI DllMain(


    HINSTANCE hinstDLL,      // Дескриптор DLL


    DWORD fdwReason,         // Причина вызова


    LPVOID lpvReserved       // Зарезервировано


)


{


    switch (fdwReason) {


        case DLL_PROCESS_ATTACH:


            // Инициализация при загрузке


            DisableThreadLibraryCalls(hinstDLL);


            break;


        case DLL_PROCESS_DETACH:


            // Очистка при выгрузке


            break;


    }


    return TRUE;


}


```


 


**Роль:**


- Стандартная точка входа для любой DLL


- Инициализация/деинициализация драйвера


- Вызывается при загрузке в Host Process


 


**2. DllGetClassObject** - фабрика объектов COM:


 


```c


HRESULT DllGetClassObject(


    REFCLSID rclsid,    // CLSID запрашиваемого класса


    REFIID riid,        // IID запрашиваемого интерфейса


    LPVOID *ppv         // Указатель на интерфейс


)


{


    if (IsEqualCLSID(rclsid, CLSID_MyDriver)) {


        // Создать и вернуть фабрику класса


        IClassFactory *pFactory = new CMyDriverFactory();


        return pFactory->QueryInterface(riid, ppv);


    }


    return CLASS_E_CLASSNOTAVAILABLE;


}


```


 


**Роль:**


- Стандартная COM-функция


- Возвращает фабрику класса (IClassFactory)


- Framework использует её для создания экземпляра драйвера


- Обязательна для любого COM-сервера


 


**3. Интерфейс IDriverEntry** - главный интерфейс драйвера:


 


```cpp


interface IDriverEntry : public IUnknown {


    // Инициализация драйвера


    HRESULT OnInitialize(


        IWDFDriver *pWdfDriver


    );


 


    // Деинициализация драйвера


    void OnDeinitialize(


        IWDFDriver *pWdfDriver


    );


 


    // Добавление нового устройства


    HRESULT OnDeviceAdd(


        IWDFDriver *pWdfDriver,


        IWDFDeviceInitialize *pWdfDeviceInit


    );


};


```


 


**Методы:**


 


**OnInitialize:**


- Аналог DriverEntry в KMDF


- Вызывается при загрузке драйвера


- Инициализация глобальных структур


- Регистрация трассировки (WPP)


 


**OnDeinitialize:**


- Вызывается при выгрузке драйвера


- Освобождение ресурсов


- Остановка трассировки


 


**OnDeviceAdd:**


- Аналог AddDevice в KMDF


- Вызывается при обнаружении нового устройства


- Создание объекта устройства (IWDFDevice)


- Настройка очередей ввода-вывода


- Регистрация callback-интерфейсов


 


**4. Callback-интерфейсы** (опциональные, но обычно необходимые):


 


**IQueueCallbackRead** - обработка чтения:


```cpp


interface IQueueCallbackRead : public IUnknown {


    void OnRead(


        IWDFIoQueue *pWdfQueue,


        IWDFIoRequest *pWdfRequest,


        SIZE_T NumOfBytesToRead


    );


};


```


 


**IQueueCallbackWrite** - обработка записи:


```cpp


interface IQueueCallbackWrite : public IUnknown {


    void OnWrite(


        IWDFIoQueue *pWdfQueue,


        IWDFIoRequest *pWdfRequest,


        SIZE_T NumOfBytesToWrite


    );


};


```


 


**IQueueCallbackDeviceIoControl** - обработка IOCTL:


```cpp


interface IQueueCallbackDeviceIoControl : public IUnknown {


    void OnDeviceIoControl(


        IWDFIoQueue *pWdfQueue,


        IWDFIoRequest *pWdfRequest,


        ULONG ControlCode,


        SIZE_T InputBufferSizeInBytes,


        SIZE_T OutputBufferSizeInBytes


    );


};


```


 


**5. Интерфейс IWDFDriver** (предоставляется Framework):


 


Драйвер получает этот интерфейс, не реализует его:


 


**Методы:**


- **CreateDevice** - создание объекта устройства


- **CreateWdfMemory** - выделение памяти


- **CreateWdfObject** - создание объектов Framework


- **IsVersionAvailable** - проверка версии Framework


 


**Минимальная структура UMDF-драйвера:**


 


```


MyDriver.dll


├── DllMain()                     // Обязательно


├── DllGetClassObject()           // Обязательно


├── CMyDriver (implements IDriverEntry)  // Обязательно


│   ├── OnInitialize()


│   ├── OnDeinitialize()


│   └── OnDeviceAdd()


└── CMyDevice (callback interfaces)  // Опционально


    ├── IQueueCallbackRead


    ├── IQueueCallbackWrite


    └── IQueueCallbackDeviceIoControl


```


 


**Дополнительные интерфейсы (по необходимости):**


- **IPnpCallback** - PnP события


- **IPnpCallbackHardware** - инициализация/освобождение оборудования


- **IFileCallbackCleanup** - очистка файла


- **IFileCallbackClose** - закрытие файла


 


**Важно:**


- Все интерфейсы основаны на COM (IUnknown)


- Необходимо правильно реализовать AddRef/Release/QueryInterface


- Framework управляет временем жизни объектов


- Ошибки в callback-функциях не приводят к BSOD, но драйвер может быть перезапущен

## 27. Что такое интерфейс IDriverEntry и какие методы он включает?


 


Интерфейс **IDriverEntry** является основным интерфейсом любого UMDF-драйвера.


 


![Интерфейс IDriverEntry](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_5.png)


 


![Интерфейс IWDFDriver](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_6.png)


 


![Дополнительные методы IWDFDriver](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_7.png)


 


### Теоретическое пояснение:


 


**IDriverEntry** - это COM-интерфейс, который должен реализовать каждый UMDF-драйвер.


 


**Определение интерфейса:**


 


```cpp


interface IDriverEntry : public IUnknown


{


    // Инициализация драйвера


    HRESULT OnInitialize(


        IWDFDriver *pWdfDriver


    );


 


    // Деинициализация драйвера


    void OnDeinitialize(


        IWDFDriver *pWdfDriver


    );


 


    // Добавление нового устройства


    HRESULT OnDeviceAdd(


        IWDFDriver *pWdfDriver,


        IWDFDeviceInitialize *pWdfDeviceInit


    );


};


```


 


**Методы интерфейса:**


 


**1. OnInitialize** - инициализация драйвера:


 


```cpp


HRESULT OnInitialize(IWDFDriver *pWdfDriver)


{


    // Сохранить указатель на объект драйвера


    m_pWdfDriver = pWdfDriver;


 


    // Инициализация WPP трассировки


    WPP_INIT_TRACING(MYDRIVER_TRACING_ID);


 


    // Инициализация глобальных структур


    InitializeCriticalSection(&m_CriticalSection);


 


    // Регистрация дополнительных компонентов


 


    return S_OK;  // Успех


}


```


 


**Параметры:**


- **pWdfDriver** - указатель на объект IWDFDriver, представляющий драйвер


 


**Назначение:**


- Аналог функции DriverEntry в KMDF


- Первая функция, вызываемая при загрузке драйвера


- Общая инициализация драйвера (не специфичная для устройства)


 


**Задачи:**


- Сохранение указателя на IWDFDriver


- Инициализация трассировки (WPP)


- Создание глобальных объектов


- Инициализация синхронизационных примитивов


- Чтение конфигурации из реестра


 


**Возврат:**


- **S_OK** (0) - успешная инициализация, драйвер загружен


- **Код ошибки** (FAILED(hr)) - драйвер будет выгружен


 


**2. OnDeinitialize** - деинициализация драйвера:


 


```cpp


void OnDeinitialize(IWDFDriver *pWdfDriver)


{


    // Остановка WPP трассировки


    WPP_CLEANUP();


 


    // Освобождение ресурсов


    DeleteCriticalSection(&m_CriticalSection);


 


    // Очистка глобальных структур


 


    // Не возвращает значение - void


}


```


 


**Параметры:**


- **pWdfDriver** - тот же объект IWDFDriver


 


**Назначение:**


- Вызывается при выгрузке драйвера


- Очистка ресурсов, выделенных в OnInitialize


 


**Задачи:**


- Остановка трассировки


- Освобождение памяти


- Закрытие дескрипторов


- Удаление синхронизационных объектов


 


**Важно:**


- Не возвращает значение (void)


- Должна успешно завершиться в любом случае


- Не должна выбрасывать исключения


 


**3. OnDeviceAdd** - добавление устройства:


 


```cpp


HRESULT OnDeviceAdd(


    IWDFDriver *pWdfDriver,


    IWDFDeviceInitialize *pWdfDeviceInit)


{


    IWDFDevice *pWdfDevice = NULL;


 


    // Настройка параметров устройства


    pWdfDeviceInit->SetLockingConstraint(None);


 


    // Создание объекта устройства


    HRESULT hr = pWdfDriver->CreateDevice(


        pWdfDeviceInit,


        NULL,  // Callback интерфейс


        &pWdfDevice


    );


 


    if (FAILED(hr)) return hr;


 


    // Создание очередей ввода-вывода


    IWDFIoQueue *pQueue = NULL;


    hr = pWdfDevice->CreateIoQueue(


        this,  // Callback объект


        TRUE,  // Default queue


        WdfIoQueueDispatchParallel,


        FALSE,


        FALSE,


        &pQueue


    );


 


    // Создание символического имени


    hr = pWdfDevice->CreateSymbolicLink(L"MyDeviceName");


 


    pWdfDevice->Release();


    return S_OK;


}


```


 


**Параметры:**


- **pWdfDriver** - объект драйвера


- **pWdfDeviceInit** - объект инициализации устройства


 


**Назначение:**


- Аналог AddDevice в KMDF


- Вызывается PnP Manager'ом при обнаружении устройства


- Создание и настройка объекта устройства


 


**Задачи:**


- Настройка параметров устройства через pWdfDeviceInit


- Создание объекта IWDFDevice


- Создание очередей ввода-вывода (IWDFIoQueue)


- Регистрация callback-интерфейсов


- Создание символических ссылок


- Настройка интерфейсов устройства


 


**Возврат:**


- **S_OK** - устройство успешно добавлено


- **Код ошибки** - устройство не будет запущено


 


**Типичная реализация класса драйвера:**


 


```cpp


class CMyDriver :


    public IDriverEntry,


    public IQueueCallbackRead,


    public IQueueCallbackWrite


{


private:


    LONG m_cRefs;  // Счетчик ссылок COM


    IWDFDriver *m_pWdfDriver;


 


public:


    // IUnknown методы


    HRESULT STDMETHODCALLTYPE QueryInterface(REFIID riid, void **ppv);


    ULONG STDMETHODCALLTYPE AddRef();


    ULONG STDMETHODCALLTYPE Release();


 


    // IDriverEntry методы


    HRESULT OnInitialize(IWDFDriver *pWdfDriver);


    void OnDeinitialize(IWDFDriver *pWdfDriver);


    HRESULT OnDeviceAdd(IWDFDriver *pWdfDriver,


                        IWDFDeviceInitialize *pWdfDeviceInit);


 


    // IQueueCallback методы


    void OnRead(IWDFIoQueue *pQueue, IWDFIoRequest *pRequest, SIZE_T size);


    void OnWrite(IWDFIoQueue *pQueue, IWDFIoRequest *pRequest, SIZE_T size);


};


```


 


**Связь с IWDFDriver:**


 


IWDFDriver - это интерфейс, предоставляемый Framework драйверу:


 


**Основные методы IWDFDriver:**


- **CreateDevice** - создание устройства


- **CreatePreallocatedWdfMemory** - выделение памяти


- **CreateWdfMemory** - создание объекта памяти


- **CreateWdfObject** - создание пользовательского объекта


- **IsVersionAvailable** - проверка версии Framework


- **RetrieveVersionString** - получение версии


 


**Жизненный цикл:**


 


1. Framework загружает DLL драйвера


2. Вызывает DllGetClassObject для получения IClassFactory


3. Создает экземпляр класса драйвера (получает IDriverEntry)


4. Вызывает OnInitialize (драйвер готов)


5. При обнаружении устройства вызывает OnDeviceAdd


6. При выгрузке вызывает OnDeinitialize


 


Интерфейс IDriverEntry - это "сердце" UMDF-драйвера, определяющее его поведение на всех этапах жизненного цикла.

## 28. Для чего используется функция DllGetClassObject в UMDF?


 


Функция **DllGetClassObject** является стандартной COM-функцией, необходимой для создания экземпляров UMDF-драйвера.


 


![Функция DllGetClassObject](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_4.png)


 


![Интерфейс IDriverEntry](extracted_images/6.СПО_Рефлизация UMDF-драйвера_page_5.png)


 


### Теоретическое пояснение:


 


**DllGetClassObject** - стандартная экспортируемая функция COM-сервера.


 


**Сигнатура:**


 


```c


HRESULT DllGetClassObject(


    REFCLSID rclsid,    // CLSID запрашиваемого класса


    REFIID riid,        // IID запрашиваемого интерфейса


    LPVOID *ppv         // Указатель на интерфейс


)


```


 


**Параметры:**


 


1. **rclsid** (REFCLSID) - Class ID (CLSID):


   - GUID, идентифицирующий класс драйвера


   - Определяется в INF-файле драйвера


   - Пример: `{12345678-1234-1234-1234-123456789ABC}`


 


2. **riid** (REFIID) - Interface ID (IID):


   - GUID запрашиваемого интерфейса


   - Обычно IID_IClassFactory или IID_IUnknown


 


3. **ppv** (LPVOID*) - указатель на возвращаемый интерфейс:


   - Выходной параметр


   - Получает указатель на фабрику класса


 


**Возвращаемые значения:**


- **S_OK** - успех, объект создан


- **CLASS_E_CLASSNOTAVAILABLE** - запрошенный CLSID не поддерживается


- **E_INVALIDARG** - некорректные параметры


- **E_OUTOFMEMORY** - недостаточно памяти


 


**Назначение:**


 


**1. Создание фабрики класса (Class Factory):**


- Framework вызывает DllGetClassObject для получения фабрики


- Фабрика - объект, который создает экземпляры драйвера


- Реализует интерфейс IClassFactory


 


**2. Инициализация драйвера:**


- Через фабрику Framework создает экземпляр класса драйвера


- Получает интерфейс IDriverEntry


- Вызывает методы IDriverEntry (OnInitialize, OnDeviceAdd)


 


**Типичная реализация:**


 


```cpp


// Фабрика класса


class CMyDriverFactory : public IClassFactory


{


private:


    LONG m_cRefs;


 


public:


    CMyDriverFactory() : m_cRefs(1) {}


 


    // IUnknown


    HRESULT STDMETHODCALLTYPE QueryInterface(REFIID riid, void **ppv)


    {


        if (IsEqualIID(riid, IID_IUnknown) ||


            IsEqualIID(riid, IID_IClassFactory))


        {


            *ppv = static_cast<IClassFactory*>(this);


            AddRef();


            return S_OK;


        }


        *ppv = NULL;


        return E_NOINTERFACE;


    }


 


    ULONG STDMETHODCALLTYPE AddRef()


    {


        return InterlockedIncrement(&m_cRefs);


    }


 


    ULONG STDMETHODCALLTYPE Release()


    {


        ULONG refs = InterlockedDecrement(&m_cRefs);


        if (refs == 0) delete this;


        return refs;


    }


 


    // IClassFactory


    HRESULT STDMETHODCALLTYPE CreateInstance(


        IUnknown *pUnkOuter,


        REFIID riid,


        void **ppv)


    {


        if (pUnkOuter != NULL)


            return CLASS_E_NOAGGREGATION;


 


        // Создать экземпляр драйвера


        CMyDriver *pDriver = new CMyDriver();


        if (pDriver == NULL)


            return E_OUTOFMEMORY;


 


        // Получить запрошенный интерфейс


        HRESULT hr = pDriver->QueryInterface(riid, ppv);


        pDriver->Release();  // Уменьшить начальный счетчик


 


        return hr;


    }


 


    HRESULT STDMETHODCALLTYPE LockServer(BOOL fLock)


    {


        // Управление временем жизни DLL


        if (fLock)


            InterlockedIncrement(&g_ServerLocks);


        else


            InterlockedDecrement(&g_ServerLocks);


        return S_OK;


    }


};


 


// Реализация DllGetClassObject


HRESULT DllGetClassObject(


    REFCLSID rclsid,


    REFIID riid,


    LPVOID *ppv)


{


    if (ppv == NULL)


        return E_INVALIDARG;


 


    *ppv = NULL;


 


    // Проверить, что запрашивается наш класс


    if (IsEqualCLSID(rclsid, CLSID_MyDriver))


    {


        // Создать фабрику класса


        CMyDriverFactory *pFactory = new CMyDriverFactory();


        if (pFactory == NULL)


            return E_OUTOFMEMORY;


 


        // Получить запрошенный интерфейс фабрики


        HRESULT hr = pFactory->QueryInterface(riid, ppv);


        pFactory->Release();


 


        return hr;


    }


 


    return CLASS_E_CLASSNOTAVAILABLE;


}


```


 


**Процесс загрузки драйвера:**


 


```


1. Driver Manager загружает MyDriver.dll


          ↓


2. Вызывает DllGetClassObject(CLSID_MyDriver, IID_IClassFactory, &pFactory)


          ↓


3. DllGetClassObject создает CMyDriverFactory и возвращает её


          ↓


4. Framework вызывает pFactory->CreateInstance(IID_IDriverEntry, &pDriver)


          ↓


5. CreateInstance создает экземпляр CMyDriver


          ↓


6. Framework получает IDriverEntry интерфейс драйвера


          ↓


7. Framework вызывает pDriver->OnInitialize()


          ↓


8. Драйвер инициализирован и готов к работе


```


 


**Связь с INF-файлом:**


 


INF-файл драйвера содержит CLSID:


 


```inf


[MyDriver_Install.Wdf]


UmdfService = MyDriver, MyDriver_Install


UmdfServiceOrder = MyDriver


 


[MyDriver_Install]


UmdfLibraryVersion = 1.11.0


ServiceBinary = %12%\UMDF\MyDriver.dll


DriverCLSID = {12345678-1234-1234-1234-123456789ABC}


```


 


**Важные моменты:**


 


1. **Обязательность**: без DllGetClassObject драйвер не загрузится


2. **COM-стандарт**: следует строгим правилам COM


3. **Фабрика**: возвращает IClassFactory, а не сам драйвер


4. **Множественные классы**: одна DLL может поддерживать несколько CLSID


5. **Управление памятью**: правильный AddRef/Release критичен


 


**Альтернативные подходы:**


 


Начиная с UMDF 2.0, можно использовать упрощенный подход без явной реализации DllGetClassObject, используя макросы WDF.

## 29. Каковы преимущества и недостатки UMDF по сравнению с KMDF?


 


UMDF и KMDF имеют различные характеристики, определяющие области их применения.


 


![Преимущества и недостатки UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_11.png)


 


![Архитектура UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_4.png)


 


![Компоненты UMDF](extracted_images/5.СПО_Структура UMDF-драйвера_page_6.png)


 


### Теоретическое пояснение:


 


**ПРЕИМУЩЕСТВА UMDF:**


 


**1. Стабильность системы:**


- Драйвер работает в пользовательском режиме (Ring 3)


- Сбой драйвера НЕ приводит к BSOD (Blue Screen of Death)


- Изолирован от ядра через механизм Reflector


- Система остается стабильной даже при критических ошибках в драйвере


 


**2. Отказоустойчивость:**


- Driver Manager автоматически перезапускает упавший Host Process


- Устройство продолжает работать после восстановления драйвера


- Нет необходимости в перезагрузке системы


 


**3. Простота разработки и отладки:**


- Стандартные инструменты отладки пользовательского режима:


  - Visual Studio Debugger


  - WinDbg (user-mode)


  - Application Verifier


- Можно использовать стандартные библиотеки C/C++


- Проще воспроизвести и диагностировать ошибки


- Быстрый цикл разработки (компиляция → тест)


 


**4. Безопасность:**


- Минимальные привилегии (LocalService account)


- Нет прямого доступа к памяти ядра


- Защита через DEP (Data Execution Prevention) и ASLR


- Ограниченный доступ к системным ресурсам


 


**5. Изоляция:**


- Каждый драйвер в отдельном процессе (опционально)


- Сбой одного драйвера не влияет на другие


- Защита от утечек памяти других драйверов


 


**6. Переносимость:**


- Проще портировать на другие архитектуры


- Меньше зависимостей от версии ОС


- COM-интерфейсы обеспечивают совместимость


 


**НЕДОСТАТКИ UMDF:**


 


**1. Производительность:**


- Дополнительные переключения контекста (user mode ↔ kernel mode)


- Копирование данных между адресными пространствами


- Накладные расходы на маршалинг через Reflector


- Не подходит для высокопроизводительных операций


 


**2. Функциональные ограничения:**


- Нет прямого доступа к прерываниям (IRQ)


- Ограниченная поддержка DMA (Direct Memory Access)


- Нет доступа к некоторым низкоуровневым API ядра


- Не может работать на IRQL > PASSIVE_LEVEL


 


**3. Задержки (Latency):**


- Увеличенное время отклика из-за межпроцессного взаимодействия


- Не подходит для устройств реального времени


- Критично для аудио, видео высокого разрешения


 


**4. Ограничения на типы драйверов:**


- Не поддерживаются:


  - Драйверы файловых систем


  - Сетевые драйверы (NDIS)


  - Драйверы видеоадаптеров


  - Драйверы Storage (disk, RAID)


  - Драйверы шин (bus drivers) в некоторых случаях


 


**5. Зависимость от инфраструктуры:**


- Требует наличия Driver Manager, Reflector, Host Process


- Дополнительное потребление ресурсов


- Больше компонентов = больше потенциальных точек отказа


 


**6. Ограниченный доступ к ресурсам:**


- Нельзя выделить физическую память напрямую


- Нет доступа к некоторым регистрам процессора


- Ограничения на работу с оборудованием


 


**СРАВНИТЕЛЬНАЯ ТАБЛИЦА:**


 


| Характеристика | UMDF | KMDF |


|----------------|------|------|


| **Режим выполнения** | User Mode (Ring 3) | Kernel Mode (Ring 0) |


| **Производительность** | Средняя/Низкая | Высокая |


| **Стабильность системы** | Высокая (нет BSOD) | Низкая (BSOD при ошибке) |


| **Отладка** | Простая (VS, WinDbg) | Сложная (kernel debugger) |


| **Безопасность** | Высокая (изоляция) | Низкая (полный доступ) |


| **Доступ к оборудованию** | Ограниченный | Полный |


| **Прерывания (IRQ)** | Нет | Да |


| **DMA** | Ограниченно | Да |


| **Задержки** | Выше | Ниже |


| **Разработка** | Проще (C++, COM) | Сложнее (C, WDM API) |


| **Тестирование** | Быстрое | Медленное |


| **Перезагрузка при сбое** | Нет | Да (BSOD) |


 


**РЕКОМЕНДАЦИИ ПО ВЫБОРУ:**


 


**Используйте UMDF для:**


- USB-устройств (принтеры, сканеры, камеры)


- Виртуальных устройств


- Протокольных драйверов


- Смарт-карт и биометрических устройств


- Простых устройств plug-and-play


- Драйверов, где стабильность важнее производительности


 


**Используйте KMDF для:**


- Сетевых адаптеров


- Storage-контроллеров (SATA, SCSI, NVMe)


- Видеоадаптеров


- Аудиоустройств реального времени


- Драйверов файловых систем


- Высокопроизводительных устройств


- Устройств, требующих обработки прерываний


- Bus drivers


 


**Гибридный подход:**


Иногда используют комбинацию: UMDF-драйвер для основной логики + тонкий KMDF-драйвер для критичных по производительности операций.

## 30. Что такое порт-драйвер и минипорт-драйвер? Приведите примеры.


 


**Порт-драйвер (Port Driver)** и **минипорт-драйвер (Miniport Driver)** - это архитектурный паттерн разделения функциональности драйвера.


 


![Типы драйверов](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_4.png)


 


![Архитектура порт-драйвера и минипорт-драйвера](extracted_images/3_СПО_Введение_в_написание_драйверов_Windows_1_page_17.png)


 


### Теоретическое пояснение:


 


**Концепция разделения:**


 


Модель **порт/минипорт** разделяет драйвер на две части:


1. **Port Driver** - общий для класса устройств


2. **Miniport Driver** - специфичный для конкретного оборудования


 


**PORT DRIVER (Порт-драйвер):**


 


**Определение:**


- Системный драйвер, предоставляемый Microsoft


- Реализует общую функциональность для класса устройств


- Абстрагирует сложность работы с подсистемой ввода-вывода Windows


 


**Функции:**


- Обработка IRP от верхнего уровня


- Управление очередями запросов


- Взаимодействие с PnP Manager и Power Manager


- Предоставление единого интерфейса для класса устройств


- Управление ресурсами (IRQ, DMA)


- Обработка ошибок и таймаутов


 


**Преимущества:**


- Разработчику не нужно разбираться в деталях WDM


- Уменьшение дублирования кода


- Единообразие интерфейса


 


**MINIPORT DRIVER (Минипорт-драйвер):**


 


**Определение:**


- Драйвер, разрабатываемый производителем оборудования


- Реализует специфичную логику для конкретного чипа/устройства


- Взаимодействует с порт-драйвером через определенный интерфейс


 


**Функции:**


- Инициализация конкретного оборудования


- Низкоуровневая работа с регистрами устройства


- Выполнение команд, специфичных для чипа


- Обработка особенностей конкретного оборудования


- Управление состоянием устройства


 


**Преимущества:**


- Упрощенная разработка (фокус только на оборудовании)


- Меньший объем кода


- Независимость от изменений в подсистеме ввода-вывода


 


**ПРИМЕРЫ:**


 


**1. USB (Universal Serial Bus):**


 


**Порт-драйверы:**


- **Usbport.sys** - универсальный USB порт-драйвер


  - Управляет USB-стеком


  - Обрабатывает URB (USB Request Blocks)


  - Управление конечными точками (endpoints)


 


**Минипорт-драйверы:**


- **Usbuhci.sys** - для USB 1.1 контроллеров (UHCI - Universal Host Controller Interface)


- **Usbohci.sys** - для USB 1.1 контроллеров (OHCI - Open Host Controller Interface)


- **Usbehci.sys** - для USB 2.0 контроллеров (EHCI - Enhanced HCI)


- **Usbxhci.sys** - для USB 3.0 контроллеров (XHCI - eXtensible HCI)


 


Каждый минипорт работает со специфичным типом USB-контроллера, но все используют общий Usbport.sys.


 


**2. Storage (Устройства хранения):**


 


**Порт-драйверы:**


- **Storport.sys** - современный порт-драйвер для хранилищ


  - Обработка SCSI команд


  - Управление очередями


  - Поддержка multipath


 


**Минипорт-драйверы:**


- **Nvme.sys** - для NVMe SSD


- **Stornvme.sys** - альтернативный драйвер NVMe


- **Iastor.sys** - для Intel SATA/RAID контроллеров


- **Amdsata.sys** - для AMD SATA контроллеров


- **Msahci.sys** - стандартный AHCI драйвер


 


**3. Сеть (NDIS - Network Driver Interface Specification):**


 


**Порт-драйвер:**


- **ndis.sys** - NDIS драйвер


  - Управление сетевыми протоколами


  - Буферизация пакетов


  - Интерфейс с TCP/IP стеком


 


**Минипорт-драйверы:**


- **e1000.sys** - Intel Ethernet адаптеры


- **r8168.sys** - Realtek PCIe Gigabit Ethernet


- **bcmwl.sys** - Broadcom Wi-Fi адаптеры


- **athrx.sys** - Atheros Wi-Fi адаптеры


 


**4. Аудио:**


 


**Порт-драйверы:**


- **Portcls.sys** - порт-драйвер для аудио (WDM Audio)


  - Управление аудио потоками


  - Микширование


  - Синхронизация


 


**Минипорт-драйверы:**


- Драйверы для конкретных звуковых чипов (Realtek, Creative, VIA и т.д.)


 


**5. Видео:**


 


**Порт-драйвер:**


- **videoprt.sys** - видео порт-драйвер


  - Управление видеопамятью


  - Взаимодействие с GDI


 


**Минипорт-драйверы:**


- Драйверы для конкретных GPU (NVIDIA, AMD, Intel)

**ИНТЕРФЕЙС МЕЖДУ ПОРТОМ И МИНИПОРТОМ:**


 


Порт-драйвер определяет набор callback-функций, которые должен реализовать минипорт:


 


**Пример (Storage Miniport):**


```c


typedef struct _HW_INITIALIZATION_DATA {


    ULONG HwInitializationDataSize;


 


    // Callback-функции, реализуемые минипортом


    PHW_INITIALIZE HwInitialize;


    PHW_STARTIO HwStartIo;


    PHW_INTERRUPT HwInterrupt;


    PHW_FIND_ADAPTER HwFindAdapter;


    PHW_RESET_BUS HwResetBus;


    PHW_DMA_STARTED HwDmaStarted;


    PHW_ADAPTER_STATE HwAdapterState;


 


    // Параметры адаптера


    ULONG DeviceExtensionSize;


    ULONG SpecificLuExtensionSize;


    ULONG SrbExtensionSize;


} HW_INITIALIZATION_DATA;


```


 


Минипорт регистрирует эти функции при инициализации:


```c


NTSTATUS DriverEntry(PDRIVER_OBJECT DriverObject,


                    PUNICODE_STRING RegistryPath)


{


    HW_INITIALIZATION_DATA hwInitData;


 


    RtlZeroMemory(&hwInitData, sizeof(HW_INITIALIZATION_DATA));


 


    hwInitData.HwInitializationDataSize = sizeof(HW_INITIALIZATION_DATA);


    hwInitData.HwInitialize = MyHwInitialize;


    hwInitData.HwStartIo = MyHwStartIo;


    hwInitData.HwInterrupt = MyHwInterruptRoutine;


    hwInitData.HwFindAdapter = MyHwFindAdapter;


    // ...


 


    return StorPortInitialize(DriverObject, RegistryPath,


                            &hwInitData, NULL);


}


```


 


**ПРЕИМУЩЕСТВА МОДЕЛИ ПОРТ/МИНИПОРТ:**


 


1. **Упрощение разработки**: производитель оборудования пишет только минипорт


2. **Переиспользование кода**: один порт-драйвер для множества устройств


3. **Стандартизация**: единый интерфейс для класса устройств


4. **Обновления**: Microsoft может улучшать порт-драйвер без изменения минипортов


5. **Тестирование**: проще тестировать небольшой минипорт


 


Эта модель широко используется в Windows для упрощения разработки драйверов и обеспечения единообразия.
